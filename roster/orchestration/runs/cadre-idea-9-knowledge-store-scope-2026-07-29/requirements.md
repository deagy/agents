## 0. Grounding correction and code-verification pass (read before the requirement tables)

Direct inspection of `agents/knowledge-store/src/cli.py`, `config.py`, `service.py`, `database.py` (2026-07-29) confirms the steward review's line-level citations and surfaces one additional implementation-level fact the review did not spell out, material to how enforcement can work at all:

- `cli.py`'s `search`/`context` subparsers define `--source` as bare `add_argument("--source")` (no default, no `required=True`) — confirmed at `cli.py` lines 34 and 42. `ingest`'s `--source` has `default="chat-export"` (line 27).
- `config.py::load_config` already computes, as a **local, unreturned variable**, exactly the fact this baseline's enforcement needs: `implicit_project_config` (line 90, set at line 97) — `True` only when no explicit `--config` was given *and* the resolved path is the one `find_project_local_config()` found by walk-up. When `implicit_project_config` is `False` and no explicit `--config` was given, resolution fell through to the global `$KNOWLEDGE_STORE_HOME` fallback tier. **This fact is computed but never exposed to `cli.py` or any caller today** — `load_config`'s return value is only the merged, resolved `config` dict, with no resolution-tier field. This is the concrete gap that makes tier-aware enforcement (steward constraint #3's "must work within existing resolution, not replace it," and this baseline's core mechanism below) currently impossible without a small, additive change to what `load_config` returns or a sibling function that exposes the same fact — recorded as Gap G-1 (§8).
- `service.py::search_store`/`build_agent_context` already treat `options.get("source")` falsy (`None` or omitted) as "no source filter" — `database.py::load_chunks` only adds the `m.source = ?` clause `if filters.get("source")` (line 125). This confirms the intent record's SC-1 baseline claim precisely: omitting `--source` today is functionally identical to "search every source," not a partial or degraded result set — it is a full, silent cross-project scan.
- `build_dispatch_plan.py`'s `_build_knowledge_context` (grounding citation, ~line 300) **always** appends a non-empty `--source` argument to every `context` invocation it constructs, sourced from `input_data["source"]`, itself derived from the target repository's origin slug or a canonical-path hash fallback — confirmed this call path never omits `--source`, so it is already compliant with every enforcement rule below without modification.
- `cli.py`'s `stats` subcommand takes **no** `--source`/`--config`-tier-aware argument at all (line 44-45) and `database.py::store_stats` (line 152) always returns a per-source breakdown of message counts across the *entire* resolved database, with no filter option whatsoever. The intent record's §5 Scope enumerates only `search`, `context`, and `ingest` — `stats` is not named. This baseline does not fold `stats` into scope (that would be an unauthorized scope expansion by this role), but records it as Gap G-6 (§8): `stats` already exposes a lower-resolution but real cross-project signal (which sources exist, how many messages each has) on the shared store with zero scoping controls, structurally the same class of gap this idea addresses for `search`/`context`/`ingest`.

No conflicts were found between the steward review's technical claims and direct code inspection; the review's line-number citations are all confirmed accurate against the file layout read here.

## 3. Functional requirements — A. Config-resolution scope signal (enabling mechanism)

Grounding: `agents/knowledge-store/src/config.py::load_config`/`default_config_path`/`find_project_local_config` (read 2026-07-29).

- **KS-FR-1:** For every invocation, the active configuration resolution must expose, to `cli.py`, which of the three tiers was used to select the config actually loaded: (a) explicit `--config`, (b) project-local `.agents/knowledge-store/config.json` found by walk-up, or (c) the global `$KNOWLEDGE_STORE_HOME` fallback. `config.py` already computes this fact internally as `implicit_project_config`; this requirement asks only that it become an observable, returned signal rather than a discarded local variable. Exact return shape (an added dict key, a second return value, a small dataclass) is a design-phase (G3) decision — see Gap G-1.
- **KS-FR-2:** The existing three-tier precedence order and resolution logic (explicit `--config` wins > project-local walk-up-to-`.git` > global fallback) must not be altered in behavior by KS-FR-1 — this is read-only exposure of an already-computed fact, not a new or modified resolution algorithm. [Operationalizes steward constraint #1.]
- **KS-FR-3:** The existing fail-closed behavior for a missing explicit `--config` (`load_config` raising `FileNotFoundError` immediately, before any merge/validation) must continue to fire before, and independently of, any new tier-based enforcement described in KS-FR-4..KS-FR-12 — new enforcement is strictly additive downstream of existing validation, never a replacement path that could soften it. [Operationalizes steward constraint #2.]

## 4. Functional requirements — B. Retrieval enforcement (`search` / `context`)

Grounding: `cli.py` lines 30-43 (`search`/`context` subparsers), `service.py::search_store`/`build_agent_context`, `database.py::load_chunks`, `agent-context.schema.json` (`source_filter` already typed `["string","null"]`).

- **KS-FR-4:** `search` and `context` gain a new boolean flag (recommended name `--all-sources`; exact flag name is a design-phase naming decision, not fixed here) that a caller passes to explicitly request cross-source retrieval, functionally equivalent to today's omitted-`--source` behavior — i.e., when passed, `options["source"]` remains `None`/absent exactly as an omitted `--source` produces today, so `database.py::load_chunks`'s existing `if filters.get("source")` clause needs no change.
- **KS-FR-5:** When the active config resolves to the global fallback tier (KS-FR-1 tier (c)) **and** neither `--source` nor `--all-sources` is supplied, `search`/`context` must reject the call with a clear, actionable error naming both remediation options (`--source <project-identifier>` to scope the query, or `--all-sources` to explicitly opt into cross-project retrieval) instead of silently ranking across every source as today. This is the core enforcement mechanism closing the gap described in intent §1/§4. [Operationalizes steward constraint #6's "not a silent flip" — see KS-NFR-2 for why a visible, fail-closed error satisfies this without a formal deprecation window.]
- **KS-FR-6:** When the active config resolves to the global fallback tier **and both** `--source` and `--all-sources` are supplied, the call must be rejected as ambiguous with a clear error, rather than silently preferring one flag over the other.
- **KS-FR-7:** When the active config resolves to tier (a) explicit `--config` or tier (b) project-local walk-up, `search`/`context` impose **no** new requirement: `--source`/`--all-sources` remain fully optional and behave exactly as today, with omission producing today's result set scoped only by whatever database that config resolves to. [Operationalizes steward constraint #3 — a real database-level partition, or a caller's own explicit `--config` choice, already provides isolation; no filter-discipline gate is layered on top of it.]
- **KS-FR-8:** When `--all-sources` is supplied against the global fallback tier, `search`/`context` must return results spanning every ingested source, identically to how an omitted `--source` behaves today — the flag exists to make deliberate cross-project retrieval an explicit, visible caller choice, not to remove the capability the steward review's constraint #7 protects. [Operationalizes steward constraint #7.]
- **KS-FR-9:** `context`'s output field `source_filter` (`build_agent_context`) must be `null` when `--all-sources` was used and the specific source string when `--source` was used — both values are already valid under `agent-context.schema.json`'s existing `"source_filter": {"type": ["string","null"]}`. No schema field addition and no schema version bump is required by this baseline. [Operationalizes steward constraint #4.]

## 5. Functional requirements — C. Ingestion enforcement

Grounding: `cli.py` lines 25-29 (`ingest` subparser, `--source` default `"chat-export"`), `service.py::ingest_file`, intent §1's identification of the generic-placeholder-default gap.

- **KS-FR-10:** When the active config resolves to the global fallback tier, `ingest` must reject a call that would otherwise fall through to the current generic default (`--source` omitted → `default="chat-export"`) with a clear, actionable error requiring an explicit, caller-supplied `--source` identifying the ingesting project. This closes the gap intent §1 identifies: "has a default, but that default is a generic placeholder, not a project identity."
- **KS-FR-11:** When the active config resolves to tier (a) or (b), `ingest` imposes **no** new requirement — the existing `default="chat-export"` behavior for project-local/explicit-config ingestion is unchanged. [Operationalizes steward constraints #3 and #6 jointly: no new requirement is imposed where a real partition or an explicit caller choice of config already exists.]
- **KS-FR-12:** There is no `--all-sources`-equivalent bypass for `ingest`. Writing content under an unscoped or placeholder identity into the shared store has no legitimate-use-case parallel to the cross-project *read* case KS-FR-8 protects, so KS-FR-10 has no opt-out flag. Recorded explicitly (not silently omitted) because a reviewer familiar with KS-FR-8's symmetry on the read side might otherwise expect one.

## 7. Non-functional requirements

- **KS-NFR-1 (scope boundary — resolves intent OD-4):** This baseline enforces *within* the existing three-tier, shared-store-plus-filter model. It does not change the default topology (a project without its own config still defaults to the shared global store), does not require any project to adopt a project-local config as a precondition for using `search`/`context`/`ingest`, and does not add a fourth resolution tier. A future decision to change the default topology (e.g., moving toward per-project stores as the default) remains a separate, materially larger Product Owner decision, explicitly out of this baseline's authority to make — matching the steward review's own lean and the intent record's own framing of OD-4.
- **KS-NFR-2 (non-silent change — resolves steward constraint #6's "explicit migration/deprecation story" requirement):** The knowledge-store CLI has no versioned release/distribution mechanism, changelog, or pinned-version consumption path — it is invoked directly from repository source via `bin/cadre`/`agents knowledge ...` at whatever commit is checked out (confirmed: no version file or CHANGELOG exists under `agents/knowledge-store/`). A fixed multi-release deprecation window is therefore not a meaningful mechanism for this component. This baseline instead operationalizes "not silent" as: (a) every rejection under KS-FR-5/KS-FR-6/KS-FR-10 is a fail-closed, non-zero-exit error with an actionable remediation message, never a narrowed-but-still-successful result; and (b) `README.md` and `SECURITY.md` are updated in the same change that ships this enforcement, describing the new requirement rather than leaving it undocumented. **This is recorded as an explicit interpretive decision by this requirements pass, not a default assumption** — grounded in constraint #6's own wording ("not a silent flip," not "must have a multi-release window"). A Product Owner may instead require a formal warn-then-enforce soft-launch phase; if so, that supersedes this NFR — tracked as Gap G-3 (§8), not silently foreclosed.
- **KS-NFR-3 (fail-fast, deterministic ordering):** Given the same resolution tier and the same combination of `--source`/`--all-sources` flags, the accept/reject decision in KS-FR-5/KS-FR-6/KS-FR-10 is deterministic and evaluable before any embedding call or database query is issued — a caller gets fast, cheap feedback on a scope violation rather than paying embedding/query cost first. [Grounds AC test design, §10.]
- **KS-NFR-4 (no dependency creep):** Implementing KS-FR-1..KS-FR-18 requires no new third-party dependency. `argparse`'s built-in mutually-exclusive-group support, or an equivalent hand-checked pair of flags matching `service.py`'s existing hand-rolled validation style (e.g. `_validate_classification`), is sufficient. [Per `library-standards.yaml`'s "prefer standard library when sufficient."] Final choice between these two equivalent low-risk options is a design-phase (G3) detail, not fixed here.
- **KS-NFR-5 (test isolation):** New tests for KS-FR-1..KS-FR-18 must not depend on `AGENTIC_SDLC_BIN` or any external/network service, consistent with `agents/knowledge-store/test/`'s existing standalone-runnable convention (the one exception already in that suite, remote-embedding tests, stub the HTTP layer rather than reaching a real network — new tests should follow the same pattern if they touch embedding at all, though KS-FR-1..KS-FR-18 do not require embedding to be exercised per KS-NFR-3).
- **KS-NFR-6 (backward compatibility — explicit per this task's instruction):** Every existing passing test in `agents/knowledge-store/test/test_knowledge_store.py` continues to pass unmodified; existing project-local-config-based retrieval/ingestion and existing `cadre select`-driven retrieval continue to succeed with identical inputs and outputs. Verified by AC-1/AC-2/AC-8 (§10).
