## 3. Functional requirements — what exactly gets bound (causal-dependency analysis)

Grounding: `build_dispatch_plan.py`, `select_agents.py`, `routing_overlay.py` (worktree), `runner-capabilities.json` (worktree) + its requirements baseline `CM-FR-13/14`, `agentic_sdlc_contracts.py`, all read in full 2026-07-29. Per the task instruction's directive, each bound field below is justified by an actual causal path into a dispatch plan's computed content, not included on a "more is safer" instinct.

- **PB-FR-1 (catalog.yaml content identity — REQUIRED):** Every dispatch plan's provenance data must include a `sha256` content hash of the exact `agents/catalog.yaml` bytes loaded by `load_catalog()` to build the `catalog` list passed into `build_dispatch_plan()`. Causal justification: `catalog` directly determines the agent-ordering (`_ordered`), validity checks (`_validate_agents`), and (transitively, per idea #8's own CM-FR-13/14 finding) every value catalog.yaml itself encodes — including manifest-derived facts already baked into catalog.yaml at generation time. Hashing catalog.yaml therefore already transitively captures the manifest's generation-time influence; see PB-FR-5.
- **PB-FR-2 (routing.yaml / effective-routing-configuration content identity — REQUIRED):** Every dispatch plan's provenance data must include a `sha256` content hash of the exact routing configuration object (`config`) passed into `build_dispatch_plan()` as loaded from disk — today, in `select_agents.py`'s actual call path, this is always the raw base `agents/orchestration/routing.yaml` bytes (see Gap G-2: no overlay resolution is wired in yet). Causal justification: `config` drives `match_routes`, `classify_risks`, `apply_cross_stack`, `_build_teams`, `_build_quality_gates`, `_gate_dispatch`, and `_matches_change_intake` — essentially all of a plan's routing-derived content.
- **PB-FR-3 (repository/commit identifier — REQUIRED when available, best-effort):** Every dispatch plan's provenance data must include, when `repository_root` is inside a git working tree and the `git` binary is resolvable (reusing `select_agents.py`'s existing `_run_git` helper/hardening, not a new git-invocation path): (a) the current `HEAD` commit SHA (`git rev-parse HEAD`), and (b) an explicit indicator of whether `agents/catalog.yaml` and the routing configuration file(s) actually loaded (base `routing.yaml`, and, once PB-FR-4 is live, any overlay file) had uncommitted modifications relative to that commit at generation time (e.g. via `git status --short -- <path>` on exactly those files). Causal justification for requiring *both* sub-fields together, not just the SHA: a bare commit SHA does not, by itself, prove which file content was actually loaded if the working tree had local uncommitted edits at generation time — SC-1/SC-2 require the auditor to determine *exactly which content* produced a plan, and a SHA alone would misrepresent a dirty-tree generation as clean. When git is unavailable (non-git checkout, git binary missing, or the lookup itself fails), these fields are omitted entirely rather than populated with a placeholder — content-hash fields (PB-FR-1/PB-FR-2) remain the load-bearing, always-present binding; git identity is supplementary, not a substitute (this mirrors OD-3's still-open mechanism-choice framing, applied here as this baseline's recommended default rather than a decision this role is authorized to finalize outright — see §6 header note).
- **PB-FR-4 (routing overlay content identity — idea #6, CONDITIONAL / currently dormant):** *If and only if* the call path that produces a dispatch plan actually resolves and applies a project-local routing overlay (i.e., the `config` object passed to `build_dispatch_plan()` is the overlay-merged effective configuration produced by `routing_overlay.merge_routing()`, not the raw base file), the plan's provenance data must additionally record: `overlay_applied: true`, a `sha256` content hash of the overlay file's exact bytes, and the overlay file's path relative to the discovering project root (per idea #6's existing walk-up-to-`.git` discovery convention). When no overlay is in effect — which, per §0's Gap G-2, is **every plan `select_agents.py` currently produces**, since it never calls into `routing_overlay.py` — these fields are omitted entirely (not `overlay_applied: false` with empty placeholders), and PB-FR-2's base `routing.yaml` hash alone is a complete, sufficient binding for that plan. This requirement defines the schema shape now (satisfying intent SC-4's extensibility expectation) but has **no observable effect until a separate integration change** wires overlay resolution into `select_agents.py`'s call path — that integration is not itself scoped by this baseline (see Gap G-2) and must not be assumed to already exist.
- **PB-FR-5 (runner-capability manifest identity — idea #8, NOT BOUND, resolved with rationale):** This baseline does **not** require binding `agents/runner-capabilities.json`'s content identity into dispatch plans, contrary to the dispatch instruction's framing hint that it is "directly relevant." Grounding: neither `build_dispatch_plan.py` nor `select_agents.py` reads `agents/runner-capabilities.json` (or any Python constant derived from it) at dispatch-plan-generation runtime — idea #8's own shipped requirements baseline (`CM-FR-13/14`) explicitly scoped the manifest to build-time/generator-only (it feeds `generate_role_metadata.py`'s validation of `catalog.yaml` and `generate_global_plugin.py`'s constants, both *upstream of* and *already captured by* hashing `catalog.yaml`/`routing.yaml` per PB-FR-1/PB-FR-2). Binding the manifest's own hash into every dispatch plan would not close any verification gap actually described in intent §3 — it would duplicate information already transitively covered, which is the "more is safer" pattern the task instruction directs against. **Extensibility headroom, not present binding:** an optional, currently-unpopulated `runner_capabilities_content_hash` provenance field is reserved in the schema (SC-4) for the scenario where a future `build_dispatch_plan.py` change begins reading the manifest directly at dispatch time (e.g. a team-dispatch runner-capability gate) — populating it before such a causal read path exists would misrepresent what actually determined the plan's content, violating C-2. This resolution corrects the dispatch instruction's framing rather than silently following it, consistent with this role's authority to ground requirements in inspected code rather than upstream assumption.

## 4. Functional requirements — verifiability strength and mechanism (resolves OD-3/OD-4)

- **PB-FR-6 (content hash, no signing — recommended default, design-confirmable):** The provenance mechanism uses `sha256` content hashing (via Python's `hashlib`, already imported and used for `dispatch_fingerprint`/the `task_id` fallback in this same module) over raw file bytes as the sole verification primitive. Cryptographic signing (e.g. `cosign`, GPG, an attestation format) is **not required** by this baseline. Rationale, addressing the task instruction's explicit question directly:
  - The stated beneficiary need (intent SC-1/SC-5: "verify — without re-trusting the process that produced the plan... the archived artifact plus independently accessible suite-state evidence (e.g. git history) is sufficient") is fully satisfiable by a reproducible content hash plus git history: a reviewer with repository access can independently recompute `sha256sum agents/catalog.yaml` at a specific commit and compare, without trusting any embedded claim from the generating process. Content hashing plus git-history cross-reference already meets that bar; signing would add non-repudiation against a *malicious* producer, which is a materially different threat model than "auditor verifies an honest-but-unproven claim" — not the problem intent §3 describes.
  - `library-standards.yaml`'s "prefer standard library when sufficient" plus C-5's new-dependency justification burden: a signing mechanism would require a signing/verification library, a key-management story, and full license/vulnerability/maintenance review not performed here (none is justified by this decomposition).
  - `team-profile.yaml`'s `cicd.artifact_signing: cosign keyless` convention is scoped to *release build artifacts* promoted through a CI pipeline with an OIDC identity — reusing it for ad hoc local `cadre select` CLI output would introduce a CI/OIDC dependency this record's C-3 (stay runnable under lightweight `unittest discover`/standalone CLI conventions) does not currently justify.
  - Idea #10 set direct precedent for exactly this kind of restraint on a structurally similar problem (validating existing hand-authored files): no new dependency, hand-written/stdlib-only default (idea #10 `SV-NFR-3`).
  - If a future design phase identifies a concrete threat model requiring defense against a malicious (not merely erroneous) plan producer, that is a new, separately-justified requirement, not an extension of today's stated need — flagged for the design phase to raise explicitly rather than assumed here.

## 5. Functional requirements — schema integration (resolves OD-5)

- **PB-FR-7 (additive/optional, not schema-required):** The new provenance content is added to `selection.schema.json` as a new top-level, optional object property (working name: `provenance`) — it is **not** added to the schema's top-level `required` array, and no existing required field, property, or `oneOf`/`additionalProperties: false` shape is modified. Rationale, addressing the task instruction's explicit question directly:
  - `selection.schema.json` is an explicit public contract (task framing) that other tooling and consuming projects may already validate against (intent §2's beneficiary: "consuming projects that archive `cadre select` output... and need that archived plan to remain independently verifiable later").
  - No concrete forcing reason was found during this decomposition for why *every* plan must carry provenance from the moment this ships — intent SC-1/SC-2 describe auditor capability *when* an archived plan carries provenance, not a claim that every historical or future plan must always carry it.
  - Making it required would be a breaking schema change for every already-archived plan under this repository's own `agents/orchestration/runs/*/` precedent and for any external consuming project's evidence trail, and would require the same kind of fixture-normalization migration idea #10's own requirements baseline had to call out for `dispatch_fingerprint`/`generated_at` (intent §5, exclusions bullet 6; see Gap G-3 below).
  - This mirrors idea #10's own explicit restraint pattern (its `OD-2`/`SV-NFR-3`: default toward the lower-commitment option absent a concrete driving reason).
  - This is a recommended, design-confirmable default per this role's authority — not a claim that a future revision could never promote it to required once downstream consumers have migrated; that promotion decision is out of this baseline's scope.

## 6. Functional requirements — lifecycle-contract-version binding (resolves OD-6)

> This role's authority does not extend to redefining the two-repo boundary itself (C-4); the analysis below applies that existing boundary to a concrete new field rather than reinterpreting it.

- **PB-FR-8 (in scope, narrowly): bind the lifecycle-contract *shape version*, not gate/approval state.** When `lifecycle_tracking.status == "integrated"`, the plan's provenance data must record the lifecycle-gates contract's own `version` field as already returned by `try_lifecycle_contract()`/`require_lifecycle_contract()` (currently pinned and checked against `agentic_sdlc_contracts.SUPPORTED_LIFECYCLE_CONTRACT_VERSION = 2`; `_fetch_contract()` already fails closed on a mismatch). When `lifecycle_tracking.status == "standalone"`, this field is absent, consistent with `lifecycle_tracking`'s existing `oneOf` shape in `selection.schema.json`.
  - **Why this does not cross the C-4 boundary:** `agentic_sdlc_contracts.py` already calls the external `agentic-sdlc` executable and already receives, parses, and version-checks a `version`-tagged contract payload as part of *Cadre's own* `build_dispatch_plan()` computation — recording that already-received, already-consumed integer alongside the plan is recording *what Cadre's own code consumed*, exactly analogous in kind to recording which `routing.yaml` content Cadre consumed (PB-FR-2). It asserts nothing about `agentic-sdlc`'s own gate-schema evolution, run-record validity, human approval status, or risk-acceptance state in the consuming project — none of which Cadre reads, infers, or echoes today, and none of which this requirement adds.
  - **What is explicitly excluded, and why:** binding a content hash or commit identifier for the *external* `agentic-sdlc` repository/kernel itself (as opposed to the `version` integer its own API already returns) would require Cadre to reach into `agentic-sdlc`'s own repository state — that is out of scope and is not proposed, because it would make Cadre a source of truth about another project's artifact identity rather than merely recording which already-consumed, already-versioned input Cadre itself used, which is the boundary C-4 actually draws (`cadre select` "emits a plan only").
  - **Resolution of OD-6:** in scope for this baseline, resolved as above — not deferred to a separate future backlog item, because the field is a narrow restatement of data the code path already receives and version-checks, with no new external dependency, new call, or new boundary-crossing introduced.

## 7. Non-functional requirements

- **PB-NFR-1 (standalone runnability, C-1/C-3):** Provenance computation must run to completion under `python3 -m unittest discover -s agents/orchestration/test -p "test_*.py"` and under direct `select_agents.py` CLI invocation, with no new external service, network call, or environment variable beyond what `build_dispatch_plan.py`/`select_agents.py` already use (`git`, `AGENTIC_SDLC_BIN`/`agentic-sdlc` when lifecycle-integrated).
- **PB-NFR-2 (zero new dependencies, C-5, `library-standards.yaml`):** Implementation must not introduce a new third-party dependency; `hashlib` (stdlib, already imported) and the existing `_run_git`-style subprocess pattern (already used for git-diff discovery) are sufficient and are this baseline's recommended default (PB-FR-6).
- **PB-NFR-3 (deterministic, fail-open on missing git, fail-closed on hash computation):** Given identical file content and identical git state, provenance output must be byte-identical across repeated runs (no embedded timestamp inside the provenance object itself — `generated_at` already serves that purpose at the plan's top level). When `repository_root` is not a git working tree, or the `git` binary is unavailable, or the git lookup itself fails, plan generation must **not** fail solely because of that — git-identity fields are omitted, content-hash fields remain present (PB-FR-3). Conversely, a failure to read/hash `catalog.yaml` or the routing configuration file itself (files already required for plan generation to proceed at all) must propagate as a hard failure, not be silently swallowed — those reads are already mandatory for existing plan generation, so provenance adds no new failure surface there.
- **PB-NFR-4 (fixture/golden-corpus normalization, related to OD-8, Gap G-3):** Any existing or future golden-corpus/fixture comparison harness that already excludes `dispatch_fingerprint`/`generated_at` from plan-equality comparison (per idea #10's requirements baseline) will need the same treatment for new provenance fields that vary by git working-tree state (`git_commit_sha`, dirty indicators, content hashes when fixtures are regenerated from a different commit) — this baseline records the need but does not itself specify or implement the normalization rule (carried forward as Gap G-3, non-blocking).
- **PB-NFR-5 (non-weakening, C-6):** Recording provenance must not be presented, documented, or implemented as, or conflated with, approval — it proves *what produced* a plan, never that the plan (or the suite state that produced it) was reviewed or approved. No change to `agent-autonomy.yaml`'s `governance` block (`approve_own_work: never`, `accept_security_or_compliance_risk: never`) is implied or permitted by this baseline.
- **PB-NFR-6 (performance):** Given file sizes as of 2026-07-29 (`catalog.yaml`/`routing.yaml` each well under 1MB; one `git rev-parse`/`git status --short` invocation), no numeric runtime budget is set here (per intent §10's restraint against inventing targets absent an approved SLA) beyond the qualitative expectation that hashing two-to-four small files and one additional git subprocess call should not become a noticeable addition to `select_agents.py`'s existing runtime, which already shells out to `git` for changed-file discovery.

## 10. Acceptance criteria

Matching idea #10's acceptance-criteria format and depth:

- **AC-1 (baseline binding correctness, SC-1):** Given a dispatch plan generated inside a clean git checkout against current on-disk `agents/catalog.yaml`/`agents/orchestration/routing.yaml`, the plan's provenance data's `catalog_content_hash`/`routing_content_hash` exactly match independently computed `sha256sum` of those two files, and `git_commit_sha` exactly matches `git rev-parse HEAD`.
- **AC-2 (determinism):** Given the same task/inputs and unchanged files, re-running plan generation twice produces byte-identical provenance content across both runs.
- **AC-3 (SC-2 — detects a later edit):** Generate plan P1 against `catalog.yaml` content C1; edit `catalog.yaml` to C2; generate plan P2 against C2 → `P1.provenance.catalog_content_hash != P2.provenance.catalog_content_hash`.
- **AC-4 (dirty-tree honesty):** With an uncommitted local edit to `routing.yaml` relative to `HEAD`, the generated plan's provenance records a dirty/uncommitted indicator for `routing.yaml` alongside `HEAD`'s own (accurately reported, not silently treated as authoritative for the actually-loaded content) commit SHA.
- **AC-5 (non-git environment, PB-NFR-3):** Generation invoked with `repository_root` outside any git working tree (or `git` unavailable) still succeeds; `catalog_content_hash`/`routing_content_hash` remain present; `git_commit_sha` and dirty-indicator fields are omitted; the schema validates successfully either way.
- **AC-6 (overlay-dormant today, SC-4, Gap G-2):** Given `select_agents.py`'s current call path (no overlay resolution wired in), every generated plan's provenance omits all overlay-specific fields — asserted by a regression test that would fail if a future change silently started fabricating overlay-provenance claims without an actual overlay-resolution call path.
- **AC-7 (manifest non-binding, negative test, PB-FR-5):** A test/code-inspection check confirms `agents/runner-capabilities.json` is not read anywhere in `build_dispatch_plan.py`/`select_agents.py`, and no dispatch plan's provenance claims a manifest content hash — a regression test that would fail if a future change silently began fabricating an unbacked manifest-identity claim without an actual causal read path.
- **AC-8 (lifecycle-contract-version binding, resolves OD-6):** With `lifecycle_tracking.status == "integrated"`, the plan's provenance records `agentic_sdlc_contract_version` equal to the contract payload's own `version` field (currently `2`); with `status == "standalone"`, the field is absent.
- **AC-9 (schema additive/backward-compatible, PB-FR-7):** A pre-change dispatch-plan JSON fixture (no `provenance` key) still validates successfully against the updated `selection.schema.json`.
- **AC-10 (dispatch_fingerprint unaffected, SC-3, PB-FR-9):** For two otherwise-identical plans that differ only in the presence/content of `provenance`, `dispatch_fingerprint` is identical across both — demonstrating `provenance` is excluded from `dispatch_fingerprint`'s canonical hashed payload, mirroring `generated_at`'s existing exclusion; the relationship is documented in `selection.schema.json`'s property description and/or `RUNBOOK.md`.
- **AC-11 (no new dependency, PB-FR-6/PB-NFR-2):** The implementation introduces zero new third-party dependencies — verified by a dependency-manifest/lockfile diff showing no addition — with content hashing implemented via stdlib `hashlib`.
