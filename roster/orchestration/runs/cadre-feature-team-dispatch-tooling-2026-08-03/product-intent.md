## 2. Users / beneficiaries

- **Anyone driving multi-agent work from outside a live Claude Code or Codex CLI session** — a human at a terminal, a script, a CI job, or a future top-level orchestrator process — who today has no way to say "dispatch this team, wait, hand me all the results" without being inside an already-running host session.
- **Codex CLI sessions using the existing MCP dispatch tool** (`roster/orchestration/mcp/dispatch_server.py` / `dispatch_core.py`), who today can only dispatch and wait on **one role at a time**, and must themselves loop N times and aggregate results to approximate a team dispatch.
- **Claude Code sessions**, who today have no tooling-based dispatch path at all in this repository — dispatch is entirely delegated to Claude Code's own plugin-provided Task/Agent mechanism (a separate repository, `deagy/cadre-plugin`), which this repository does not control and which is exactly the "plugin" the raw request asks to move away from.
- **Maintainers of `roster/orchestration/mcp/`**, who inherit whatever safety-control surface (classification/sandbox narrowing, dispatch-depth guard, confirmation gating, concurrency limiting, audit logging — see Section 6) this feature must extend rather than bypass.
- **Reviewers of this repository's dispatch/routing/approval-adjacent code**, who rely on the authorship/approval-separation invariant (`roster/shared/agent-autonomy.yaml`, `CLAUDE.md`'s "hard invariant" note) holding across any new dispatch surface, not just the existing one.

## 3. Problem statement (WHAT and WHY)

**What exists today, verified by reading the code, not assumed from the raw request:**

- `bin/cadre select` (`roster/orchestration/src/select_agents.py` / `build_dispatch_plan.py`) is a deterministic **planning** tool. It emits a JSON dispatch plan — routes, primary/review/support roles, a `teams` array derived from `routing.yaml`'s `team_recipes`, applicable lifecycle gates — and explicitly never invokes an agent, retrieves knowledge, approves a gate, merges, or deploys (`README.md`: *"The selector emits a plan only. It does not run agents, retrieve knowledge, deploy, mutate infrastructure, merge, push, or approve anything."*, echoed in `CLAUDE.md` and `roster/RUNBOOK.md`). This boundary is a repeatedly-stated architectural invariant, not an oversight.
- Real subprocess-spawning dispatch tooling for **exactly one role at a time** already exists, and is the closest prior art to "tooling rather than plugins": `roster/orchestration/mcp/dispatch_server.py` (a stdio MCP server exposing a single `dispatch_secure_cloud_role` tool) and `roster/orchestration/mcp/dispatch_core.py` (the actual logic — role resolution across a three-tier project/global/plugin lookup, `validate_classification()`, `compute_effective_sandbox()`, a `MAX_DISPATCH_DEPTH` re-dispatch guard, a two-call `ConfirmationGate` for write-capable dispatch, a `ConcurrencyLimiter`, and `write_audit_record()`; `spawn_and_wait()` does the actual `codex exec` subprocess spawn, stdin prompt feed, wall-clock timeout with process-group kill, and capped stdout capture).
- This mechanism has three concrete gaps relative to the raw request, confirmed by reading `dispatch_core.py` in full:
  1. **Single-role only.** `dispatch_secure_cloud_role()` resolves and spawns exactly one `role_id` per call; there is no team-shaped input, no fan-out, and no "wait for all N to finish and aggregate" behavior anywhere in this module. A caller wanting a team today must itself invoke the tool N times and reassemble results — the tool does not do this for them.
  2. **Codex-only.** `build_child_argv()` hardcodes a `codex exec ...` argv. There is no equivalent path in this module for spawning a Claude Code child (e.g., a headless `claude -p` invocation) or any other runner; the Claude Code side of "dispatch teams or individual agents" is entirely unaddressed by this mechanism as it stands.
  3. **Only reachable from inside a running Codex session.** The server is a stdio MCP tool (`dispatch_server.py`); it is invoked by a model's tool call, not by a standalone command a human, script, or CI job could run directly. There is no CLI subcommand under `bin/cadre` that does what this module does.
- **A related, incidental finding surfaced while verifying this baseline** (not part of this feature's problem statement, but material context for anyone building on this module): `dispatch_core.py`'s `CATALOG_PATH` is computed as `REPOSITORY_ROOT / "agents" / "catalog.yaml"` (line 48), which resolves to a nonexistent `cadre/agents/catalog.yaml` against this repository's actual current layout (`roster/catalog.yaml`, post-rename per `AGENTS.md`/`CLAUDE.md`'s current terminology). `load_known_role_ids()`'s default call would fail with `DispatchUnavailable` against a real, uninstrumented invocation of `dispatch_secure_cloud_role()` in this repository today; the existing test suite (`roster/orchestration/test/test_mcp_dispatch.py`, 94 tests, all passing as of this record) does not catch this because every test that reaches role resolution passes an explicit `catalog_path` fixture rather than relying on the module default. This is flagged here as a fact discovered during verification, not fixed by this planning-only record — see Open Decision OD-8.

**Desired outcome, as best this record can state it without over-resolving an ambiguous request (see Section 11, OD-1):** someone who wants a subset of the roster's agents to do work — a single named role, or a `routing.yaml` team recipe / ad hoc set of roles — should be able to trigger that work through this repository's own tooling (not a host CLI's plugin/subagent mechanism), and be able to wait for the whole set to finish and receive an aggregated, per-member result, rather than manually looping single-role calls or relying entirely on a plugin the requester explicitly wants to move away from.

## 4. Scope

In scope for this intent (the *problem space*, not an implementation mandate — implementation approach is a requirements/design decision per this role's authority limits):

- A dispatch mechanism, reachable through this repository's own tooling, that accepts **more than one role at a time** — whether expressed as an explicit list of `role_id`s, a `routing.yaml` `team_recipes` entry, or both — and returns once **all** members have completed (or otherwise reached a terminal state: denied, unavailable, timed out), with per-member results distinguishable from one another.
- Preserving `cadre select`'s existing planning-only contract exactly as documented in `README.md`/`CLAUDE.md` (see Section 9, Central tension) unless and until a human Product Owner explicitly decides otherwise.
- Extending, not replacing, the existing single-role safety-control surface in `dispatch_core.py` (classification/sandbox narrowing, confirmation gating, dispatch-depth guard, concurrency limiting, audit logging) to a team-aware shape — see Section 6 for the specific per-control questions this raises.
- The existing Codex-only, MCP-only mechanism as the evidence/test baseline to extend (`roster/orchestration/test/test_mcp_dispatch.py`, `roster/orchestration/mcp/SECURITY-CONTROLS.md`), per this role's instruction to cite rather than replace it.

## 6. Constraints

Traced to existing approved repository policy and code, not invented:

- **C-1 (`roster/shared/agent-autonomy.yaml`, `CLAUDE.md`'s "hard invariant"):** authorship/approval separation must hold across any new dispatch surface exactly as it holds today — no dispatched agent, individually or as part of a team, may approve its own work, self-authorize production/destructive action, or fabricate approval evidence.
- **C-2 (existing per-role controls in `dispatch_core.py`, each of which needs an explicit team-aware analogue, not a silent drop):**
  - *Classification/sandbox narrowing* (`validate_classification()`, `compute_effective_sandbox()`) — does every team member get independently narrowed against the same parent classification, or does the team as a whole get one ceiling?
  - *Dispatch-depth guard* (`MAX_DISPATCH_DEPTH = 1`, documented in `SECURITY-CONTROLS.md` as advisory-only against an adversarial child) — what stops a team from spawning teams? A per-member depth counter alone does not obviously answer "how many total agents can a single top-level request ultimately cause to run."
  - *Confirmation gating* (`ConfirmationGate`, a two-call TTL-bound token scheme) — does a team dispatch need one confirmation covering the whole team, or one per write-capable member? A single team-wide token risks masking which specific members are write-capable; N per-member tokens risk being harder for a human to review as a coherent unit.
  - *Concurrency limiting* (`ConcurrencyLimiter`, currently `MAX_CONCURRENT_CHILDREN = 3` process-wide) — does a team of N need its own team-scoped cap distinct from the existing global cap, so one large team dispatch can't itself starve the global limiter for unrelated concurrent single-role dispatches?
  - *Audit logging* (`write_audit_record()`, one JSON-lines record per single-role dispatch outcome today) — does a team dispatch produce one audit record per member (matching today's shape, but needing a shared correlation identifier across the team) or one aggregate record, or both? `SECURITY-CONTROLS.md`'s existing "mechanically enforced vs. advisory" framing must be re-derived, not silently assumed to transfer, for whatever the answer is.
- **C-3 (`roster/shared/library-standards.yaml`):** any new dependency needs documented technical rationale, pinned version, license review, and vulnerability/supply-chain review before adoption.
- **C-4 (this role's authority limit, `roster/planning/product-intent-agent/AGENT.md`):** this record may not mandate an implementation approach, a priority, or a scope expansion/cancellation; it may only state the problem, desired outcome, and flag tradeoffs as open.
- **C-5 (`roster/shared/operating-principles.md`):** must not silently weaken existing tests, security controls, or approval gates — in particular, must not weaken or replace `roster/orchestration/test/test_mcp_dispatch.py`'s existing single-role coverage or `SECURITY-CONTROLS.md`'s existing enforced/advisory claims as a side effect of adding team support.
- **C-6 (two-repo boundary, `CLAUDE.md`):** must not move lifecycle gate schemas, run-record validation, or gate-authority semantics into this repository — those remain permanently owned by `deagy/agentic-sdlc`. A team-dispatch mechanism built here supplies dispatch inputs/execution, not lifecycle-gate approval logic.

## 9. Conflicts

**Central tension (see Open Decision OD-1 in Section 11, listed first because it determines the shape of everything else):** `CLAUDE.md`'s and `README.md`'s stated architectural boundary — *"cadre select emits a plan only... it never retrieves knowledge, invokes agents, approves gates, merges, deploys, or mutates infrastructure"* — describes the deterministic **selection** command specifically. The existing MCP dispatch server (`dispatch_core.py`/`dispatch_server.py`) already establishes, as shipped prior art, that a **separate, explicitly gated, opt-in execution layer** can coexist with that boundary without violating it: it never touches `cadre select`'s own code path or output contract, it is reached through an entirely different entry point (an MCP tool call, not `bin/cadre select`), and it carries its own independent safety-control surface (Section 6). This is a real, unresolved fork in how this feature could be built, and this record deliberately does not resolve it:

- **Reading A:** build the new team/runner-neutral capability as a generalization of that same opt-in, safety-gated execution layer — team-aware, possibly runner-neutral — while leaving `cadre select` exactly as documented today (plan-only, no execution). This preserves the existing boundary statement's literal truth unmodified.
- **Reading B:** the requester wants something that changes what `cadre select` itself does — e.g., an execution mode or a companion command tightly coupled to selection's own output, blurring today's plan-then-separately-dispatch two-step into one. This would require rewriting the boundary statement in `README.md`/`CLAUDE.md`, not just adding new tooling alongside it.

Nothing in the raw request or in the additional context supplied for this dispatch states which reading is intended, and this role's authority does not extend to picking one. This is escalated as OD-1.

No other conflicting objectives were found between this intent and other read sources.

## 10. Success criteria (measurable, not target-inventing)

Per this role's constraint against inventing targets/commitments/priorities, these are framed as observable conditions the eventual requirements/design/build phases can verify against:

- **SC-1:** A caller can request dispatch of more than one role (named individually or via a team recipe) through this repository's own tooling and receive a single response only after every member has reached a terminal state (completed, denied, unavailable, or timed out) — demonstrable via a test that dispatches a team of at least two members with staggered completion times and asserts the caller's wait does not return until the slowest member finishes.
- **SC-2:** Each team member's result (status, exit/decision outcome, timing, output) is individually distinguishable in the aggregated response, not merged into a single undifferentiated blob — demonstrable via a team dispatch where members intentionally produce different outcomes (e.g. one denied, one dispatched) and asserting both are separately visible.
- **SC-3:** Every existing single-role safety control this record enumerated in Section 6 (classification/sandbox narrowing, dispatch-depth guard, confirmation gating, concurrency limiting, audit logging) has an explicit, documented team-aware behavior — not a silent inheritance assumption — before the feature is considered complete, matching `SECURITY-CONTROLS.md`'s existing convention of stating mechanically-enforced vs. advisory for each control.
- **SC-4:** The existing single-role mechanism's current test baseline (`roster/orchestration/test/test_mcp_dispatch.py`, 94 tests as of this record) continues to pass unmodified, and `SECURITY-CONTROLS.md`'s existing enforced/advisory claims remain accurate for the single-role path — i.e., team support is additive, not a replacement that could regress or reinterpret single-role behavior (traced to constraint C-5).
- **SC-5:** Whichever of the three readings in Section 5's first bullet (generalize existing Codex/MCP mechanism; new runner-neutral standalone CLI; Claude Code equivalent) is selected by the Product Owner is explicitly recorded as a decision before requirements decomposition proceeds, rather than inferred silently from whichever one gets built first.

Numeric targets (e.g. maximum team size, wait timeout budget, specific CI gating behavior) are intentionally not set here — they are a requirements/design decision per this role's constraint against inventing commitments.

## Implementation addendum (2026-08-03, same day)

A session-scoped goal directive ("implement the plan," with an explicit instruction not to pause and ask) was set on this repository after this intent record was drafted, before a human Product Owner had reviewed or approved it. This addendum records, transparently, that engineering proceeded under that directive rather than under a Product Owner's G1 approval, and exactly which open decisions were resolved by unilateral engineering judgment as a result versus which remain genuinely open. **This addendum is not a substitute for G1 approval** — a human should still review OD-1/OD-2 and confirm or overturn the calls made below.

Decisions made to proceed, each traceable to a specific code change:
- **OD-1 resolved as Reading A**: built as a generalization of the existing opt-in, safety-gated MCP execution layer (`dispatch_core.py`/`dispatch_server.py`); `bin/cadre select` was not touched, and its plan-only contract is unchanged.
- **OD-3/OD-7 resolved as the smallest increment**: extended the existing Codex-only MCP surface with a new `dispatch_team()` function and `dispatch_team` MCP tool, rather than building a new standalone `bin/cadre` subcommand or a new runner-neutral CLI.
- **OD-4 resolved as deferred**: Claude Code child-process support is explicitly out of scope for this increment; `build_child_argv()` still only builds `codex exec` invocations.
- **OD-5 resolved** with specific, documented defaults for every sub-question (classification/sandbox: per-member independent narrowing; depth guard: checked once per team, no separate fan-out cap beyond a new `MAX_TEAM_SIZE = 8`; confirmation gating: one team-wide token covering every member, listing which are write-capable; concurrency: shared with the existing global `ConcurrencyLimiter`, via a new blocking `acquire()` that queues instead of denying; audit: one record per member plus one team-summary record, correlated by a new `team_id`). Full rationale in `roster/orchestration/mcp/SECURITY-CONTROLS.md`'s new "Team dispatch" section.
- **OD-6 resolved**: team membership is an explicit `{"role_id", "brief"}` list per call, not built on `routing.yaml`'s `team_recipes` directly in this increment (a caller can still supply a recipe's member list manually; wiring `team_recipes` resolution in is a natural follow-up, not done here).
- **OD-8 resolved**: the `CATALOG_PATH` regression was fixed directly (`roster/orchestration/mcp/dispatch_core.py`, one line), independent of and before this feature's design work, since it was an isolated bug with no bearing on OD-1.

Still open, unaffected by this implementation: **OD-2** (no Product Owner named for this repository's feature intake in general — still true).
