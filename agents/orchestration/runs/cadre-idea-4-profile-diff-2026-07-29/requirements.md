## 3. Functional requirements — input resolution and comparison surface

Grounding: intent §3-§4, `plugins/cadre/provider.json` (`id: "cadre"`, `version: "0.3.0"`, `kernel_compatibility.minimum`/`maximum_exclusive`, `profile_roots`), `plugins/cadre/profiles/secure-cloud/profile.json` (`id`, `version`, `extends`, `agents[]`, `routing[]`, `impact_categories[]`), `agents/RUNBOOK.md` §16 ("generated project wrappers are static copies bound to that provider version" / "preserve the version lock with the reviewed overlay").

- **PD-FR-1:** The comparison surface is the field-level content of `plugins/cadre/provider.json` and `plugins/cadre/profiles/<profile-id>/profile.json` (or `profiles/generic/profile.json` for non-Secure-Cloud adopters), not any other release artifact (e.g. not `plugins/cadre/agent-catalog.json`'s full content, not the generated Claude/Codex subagent wrapper bodies) — scoped to the two files the intent record names, per its §4/§5 framing.
- **PD-FR-2:** The tool accepts three logically distinct inputs, however they are physically supplied (file path, directory root, or — if a later design decision resolves OD-2's placement question toward a kernel-exposed read — a kernel-provided record): (a) this suite's *current* released provider/profile artifact content ("CURRENT"), (b) the consuming project's *currently present* copy of that material ("COPY"), and (c) the *originally captured* provider/profile content the project's copy was initialized from, identified by the version recorded in the project's own version-lock ("ORIGINAL"). Exactly how ORIGINAL is obtained (a caller-supplied snapshot file, a lookup against this suite's tagged-release history by version number, or something else) is a design decision — see OD-2 in §6 — but the comparison logic requires all three as a matter of requirements, not two.
- **PD-FR-3:** If ORIGINAL cannot be resolved (e.g. no version-lock record found, or the recorded version cannot be located in this suite's release history), the tool reports this as a distinct, explicit condition ("provenance undetermined") rather than silently defaulting ORIGINAL to CURRENT or to COPY, either of which would produce an incorrect classification per §4 below.
- **PD-FR-4:** If COPY itself fails basic structural validation (malformed JSON, missing required top-level fields such as `id`/`version` for `provider.json` or `id`/`version`/`agents` for `profile.json`) the tool reports this as a distinct "copy invalid" condition, not as "diverged" — a corrupted or hand-broken copy is not the same finding class as a deliberate, well-formed local customization (this resolves intent OD-3's "customized vs. corrupted/invalid" question — see §6).

## 4. Functional requirements — three-state (plus two degenerate) classification

Grounding: intent §3 (three-state framing), §10 SC-1/SC-2/SC-3.

- **PD-FR-5:** The tool classifies a resolved (CURRENT, ORIGINAL, COPY) triple into exactly one of the following states, evaluated in this priority order (first match wins):
  1. **`copy-invalid`** — COPY fails structural validation (PD-FR-4). Checked first because a structurally invalid copy cannot be meaningfully field-compared at all.
  2. **`provenance-undetermined`** — ORIGINAL could not be resolved (PD-FR-3). Checked second because without ORIGINAL, `stale-unmodified` cannot be distinguished from `diverged`.
  3. **`current`** — COPY is field-for-field identical to CURRENT.
  4. **`stale-unmodified`** — COPY is field-for-field identical to ORIGINAL, and ORIGINAL is *not* field-for-field identical to CURRENT (i.e. the suite has moved on since the project's copy was captured, but the project has not locally edited its copy).
  5. **`diverged`** — COPY is field-for-field identical to neither CURRENT nor ORIGINAL (the project has locally modified its copy since capture, independent of whether the suite has also since changed).
- **PD-FR-6 (current, testable):** Given COPY == CURRENT field-for-field, the tool reports state `current` regardless of whether COPY also happens to equal ORIGINAL (i.e. no drift has occurred since capture) or differs from ORIGINAL (i.e. a hand-edit happened to land the copy exactly on the current release's content) — the classification is defined purely by COPY-vs-CURRENT equality, not by edit history, per the priority order in PD-FR-5.
- **PD-FR-7 (stale-unmodified, testable):** Given COPY == ORIGINAL field-for-field and ORIGINAL != CURRENT field-for-field, the tool reports state `stale-unmodified` and does not report `diverged`, even though ORIGINAL and CURRENT differ — the divergence is between the suite's release and the project's copy's origin, not between the project's copy and its own origin.
- **PD-FR-8 (diverged, testable):** Given COPY != ORIGINAL field-for-field (and COPY != CURRENT, else PD-FR-6 applies), the tool reports state `diverged` regardless of whether ORIGINAL == CURRENT (the project edited a copy that was, at capture time, already current) or ORIGINAL != CURRENT (the project edited a copy that was already behind) — both are `diverged`, but PD-FR-11 requires the report to separately surface which sub-case applies since they call for different remediation framing (reconcile a customization vs. reconcile a customization *and* catch up to a newer release).
- **PD-FR-9 (this resolves intent OD-3's scope question):** `diverged` is affirmatively in scope for this baseline, not deferred — the intent record's own three-state framing (§3, §4 bullet 2, SC-2) requires distinguishing it from staleness, and Assumption A-3 is confirmed rather than left open: local customization of a provider/profile copy is treated as a legitimate, expected state to detect and report (not an error condition), symmetric with how `agents/shared/README.md` already documents overlay customization as supported for the mechanistically different `agents/shared/*` case.

## 5. Functional requirements — reporting content and precision

Grounding: intent §4 bullet 3, §10 SC-1/SC-2/SC-5, C-4.

- **PD-FR-10 (field-level precision, per SC-1/SC-5):** For any state other than `current`, the report names, per differing field, at minimum: the artifact (`provider.json` or `profile.json`), the field path (e.g. `kernel_compatibility.maximum_exclusive`, `agents[]` membership diff, `routing[].id="frontend".reviewers[]`), and the old vs. new value (or added/removed set membership for list fields such as `agents[]` and `routing[]`). A finding that only reports "profile.json differs" without field-level detail does not satisfy this requirement.
- **PD-FR-11 (state-appropriate framing, per PD-FR-8):** For `stale-unmodified`, the report frames every finding as CURRENT-vs-ORIGINAL (what the project would gain by re-syncing). For `diverged`, the report frames findings as COPY-vs-ORIGINAL (what was locally changed) and, separately, notes whether ORIGINAL also differs from CURRENT (whether the suite has additionally moved on) — the report must not collapse these into a single undifferentiated diff when the underlying comparison is `diverged`, per PD-FR-8's remediation-framing rationale.
- **PD-FR-12 (exhaustive-per-run reporting):** A single run against a copy with multiple independent field differences reports all of them in one pass, not just the first — needed for SC-1/SC-2's fixtures to remain demonstrable when a fixture intentionally carries more than one differing field for test economy (mirrors idea #10's SV-FR-26 precedent).

## 6. Functional requirements — boundary (must-never rules)

Grounding: intent §5 exclusions, §6 C-1/C-2/C-3, `CLAUDE.md` "Two-repo boundary", `docs/lifecycle-and-plugin-operations.md`, `agents/shared/agent-autonomy.yaml` `governance` block. This is the dispatch instruction's central resolution target — stated as concrete, testable rules, matching the pattern requested from idea #6's (not-yet-written) routing-overlay safety-boundary requirements.

- **PD-FR-13 (read-only against the consuming project, hard rule):** The tool MUST NOT write to, modify, or delete any file, record, or field belonging to the consuming project — including its `.agentic-sdlc/` records, its version-lock record, and its copied provider/profile material itself. It reads COPY and whatever version-lock/original-snapshot reference is available; it never updates them, even to "fix" a detected drift. A run that leaves the target project's filesystem state unchanged (byte-for-byte, before vs. after) satisfies this requirement; any write is a defect.
- **PD-FR-14 (no re-sync/remediation action, hard rule):** The tool MUST NOT apply, propose as a default action, or offer a one-command mechanism to overwrite COPY with CURRENT or ORIGINAL. It produces a report only; any re-sync remains a separate, human-reviewed action outside this idea's scope (per intent §5 and `docs/lifecycle-and-plugin-operations.md`'s "Plugin upgrades never grant approval or rewrite project decisions automatically").
- **PD-FR-15 (no gate-approval or lock-state interpretation, hard rule):** The tool MUST NOT read, interpret, or report on the consuming project's gate-approval state, human-authority assignments, risk-acceptance decisions, or any other `.agentic-sdlc/` run-record content beyond the narrow provider/profile version-lock reference needed to resolve ORIGINAL (PD-FR-2). It must not claim, imply, or produce output framed as "this project's lifecycle records are valid," "this project is compliant," or any other authoritative statement about that project's gate state — those are `deagy/agentic-sdlc`'s and that project's own owned concerns, never this suite's, per `CLAUDE.md`'s permanent two-repo boundary.
- **PD-FR-16 (not an approval or authorization signal, hard rule, per C-2):** The report's output MUST NOT be labeled, formatted, or documented in a way that could be mistaken for an approval, a passed gate, or an authorization to proceed (e.g. no bare "PASS"/"OK" on a `current` result framed as gate clearance) — it is drift information for a human to act on, consistent with `agent-autonomy.yaml`'s `governance.approve_own_work: never` / `authorize_production_release: never`.
- **PD-FR-17 (this repository owns only the release-artifact side, per C-1/C-5):** Whatever code eventually implements this comparison, this repository's own contribution is limited to supplying its current release artifacts (`provider.json`/`profile.json` content) and the comparison/reporting logic over caller-supplied or kernel-exposed inputs — it must not grow logic that independently interprets or validates the *shape* of `.agentic-sdlc/` run records, schemas, or gate definitions, since that ownership is `deagy/agentic-sdlc`'s permanently (`CLAUDE.md`).

## 7. Functional requirements — CLI shape (design-confirmable recommendation, not mandated)

Grounding: intent §5 ("implementation approach is not decided here" / OD-5), C-5 (this role may not decide implementation), `bin/subcommands.tsv`, `bin/cadre`, `agents/orchestration/src/generate_role_metadata.py`'s `--check` convention, `agents/orchestration/src/plugin_version.py`'s `--check`/`--set` convention.

- **PD-FR-18 (recommended, not mandated, per C-5):** If the design phase adopts a new subcommand (matching the backlog's literal `cadre profile diff` name), it should follow the existing dispatch-table pattern: a new `profile` row (or `profile diff` sub-mode) in `bin/subcommands.tsv` pointing at a new script under `agents/orchestration/src/`, dispatched the same way `select`/`knowledge`/`version`/`resolve-shared` already are — no new dispatch mechanism. Because a diff report is inherently richer than a pass/fail check, the recommendation is: (a) a human-readable multi-line report to stdout by default, one block per differing field per PD-FR-10, headed by the resolved state (`current`/`stale-unmodified`/`diverged`/`copy-invalid`/`provenance-undetermined`); (b) exit code 0 for `current`, non-zero for every other state (reusing the `--check`-style "non-zero means action may be warranted" convention from `plugin_version.py`/`generate_role_metadata.py`, while noting a diff tool's non-zero does not mean "invalid" the way those tools' non-zero does — a distinction the design phase should make explicit in its own `--help` text); (c) an optional machine-readable mode (e.g. `--json`) for a consuming project's own CI to consume, since intent §5 leaves CI integration cadence undecided (OD-5's cadence sub-question) and a stable machine-readable shape keeps that door open without this baseline mandating it. None of (a)-(c) is binding on the build phase; C-5 reserves the final CLI/format decision to requirements/design as intent itself states.

## 8. Non-functional requirements

- **PD-NFR-1 (environment scope, intent §7):** The tool operates only against this suite's own release artifacts and a consuming project's local files/records supplied to it (by path or by whatever mechanism OD-2's placement decision settles on) — it never touches Proxmox, Talos, Kubernetes, or any production/staging surface in either repository, and `agent-autonomy.yaml`'s persistent/staging/production mutation-approval tiers are not implicated by running it (mirrors intent §7 verbatim).
- **PD-NFR-2 (deterministic, fail-closed):** Given the same three resolved inputs (CURRENT, ORIGINAL, COPY), the tool produces the same classification and finding list on every run. A structurally-invalid input file is a reportable condition (PD-FR-4), not a silent pass or an unhandled crash.
- **PD-NFR-3 (no compliance-framework or evidence-retention scope creep):** Per `agents/shared/team-profile.yaml`'s `out_of_scope_standards` block, this baseline does not introduce or assume any named compliance-framework obligation (SOC 2, ISO 27001, etc.) for the report's content or retention — it is an internal-tooling drift report, not a compliance artifact, unless a future decision makes that material.
- **PD-NFR-4 (no dependency or performance commitment, intent §5):** No new third-party dependency, runtime budget, or SLA is mandated by this baseline; if JSON-diffing needs exceed what a hand-rolled comparison (mirroring `provider.json`/`profile.json`'s already-small, already hand-authored/JSON-syntax shape) can reasonably provide, `library-standards.yaml`'s new-dependency justification, pinned version, and license/vulnerability review apply before one is added — this is a note for the design phase, not a decision made here (mirrors idea #10's SV-NFR-3 treatment of the same question for a structurally similar comparison problem).
- **PD-NFR-5 (no cadence/automation commitment, intent §5):** Whether this becomes a scheduled check, an on-demand command, or a consuming project's own CI step is explicitly not decided here (OD-5's cadence sub-question, carried forward).
- **PD-NFR-6 (scope boundary vs. `agents/shared/*` overlay resolution, per A-1/OD-4):** This baseline's requirements apply to the provider/profile static-copy mechanism only, not to `agents/shared/*` overlay resolution — the tool must not be built or tested assuming it also needs to detect `resolve-shared` staleness, since that mechanism is architecturally a live resolution (always reads the current default, per `agents/shared/README.md`/`resolve.py`), not a point-in-time snapshot, and therefore is not the same drift problem (this resolves OD-4 for this baseline — see §6 below for the disposition).

## 11. Acceptance criteria

Matching idea #10's acceptance-criteria format and depth:

- **AC-1 (clean/current baseline, SC-3):** Given COPY identical to CURRENT, the tool reports state `current` with zero findings, no false positives.
- **AC-2 (stale-unmodified fixture, SC-1):** Given a fixture pairing an older provider/profile snapshot (as ORIGINAL, matching COPY exactly) against a current snapshot with at least one changed field (e.g. an added `agents[]` entry, a changed `kernel_compatibility.maximum_exclusive`, a changed `routing[]` entry) as CURRENT, the tool reports state `stale-unmodified` and names each changed field, old value, and new value (PD-FR-6, PD-FR-7, PD-FR-10).
- **AC-3 (diverged-at-current-version fixture, SC-2):** Given ORIGINAL == CURRENT (the project's copy was captured at the current release) but COPY has been hand-edited (e.g. a `routing[]` entry's `reviewers[]` list modified), the tool reports state `diverged`, names the edited field(s) as COPY-vs-ORIGINAL differences, and does not also report `stale-unmodified` (PD-FR-8, PD-FR-11).
- **AC-4 (diverged-and-behind fixture, SC-2):** Given ORIGINAL != CURRENT (the suite has moved on) and COPY != ORIGINAL (the project also hand-edited its copy), the tool reports state `diverged`, and the report additionally notes that ORIGINAL and CURRENT differ (PD-FR-8's sub-case note, PD-FR-11).
- **AC-5 (copy-invalid fixture):** Given a COPY that is malformed JSON or missing a required field (e.g. no `id` in `profile.json`), the tool reports state `copy-invalid`, distinct from `diverged`, and does not attempt a field-level diff against it (PD-FR-4, PD-FR-5).
- **AC-6 (provenance-undetermined fixture):** Given no resolvable ORIGINAL (e.g. no version-lock reference supplied, or a referenced version that cannot be located), the tool reports state `provenance-undetermined` rather than defaulting ORIGINAL to CURRENT or COPY (PD-FR-3).
- **AC-7 (multi-field single-pass reporting):** A fixture with at least two independent field differences in one comparison → a single run reports both, not just the first (PD-FR-12).
- **AC-8 (read-only demonstration, SC-4, PD-FR-13/PD-FR-14):** Running the tool against a fixture pair (release-artifact-side files plus a simulated consuming-project directory) leaves every file byte-for-byte unchanged (before-vs-after comparison), across all six classification states in AC-1..AC-6 — no state's handling path performs a write.
- **AC-9 (non-authoritative boundary demonstration, PD-FR-15/PD-FR-16):** A code-review or test-level check confirms the tool's implementation reads no field from a consuming project's records beyond the provider/profile version-lock reference needed for ORIGINAL resolution (PD-FR-2), and that no report output string claims or implies gate-approval, compliance, or authorization status.
